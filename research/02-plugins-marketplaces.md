# Claude Code Plugins & Marketplaces: Declarative vs. CLI-Dependent

## Summary

**Recommendation: SPLIT MODEL** — Marketplace registration and plugin enable/disable can be files-first via `settings.json`. Plugin *installation* requires the CLI to fetch content from remote repositories, but the declarative *specification* (what to install, what's enabled, what version constraints apply) can live in config files.

---

## 1. File Representation of Plugins & Marketplaces

### 1.1 Plugin Installation Metadata

**File**: `~/.claude/plugins/installed_plugins.json`

```json
{
  "version": 2,
  "plugins": {
    "rust-analyzer-lsp@claude-plugins-official": [
      {
        "scope": "user",
        "installPath": "/home/wil/.claude/plugins/cache/claude-plugins-official/rust-analyzer-lsp/1.0.0",
        "version": "1.0.0",
        "installedAt": "2026-02-06T02:59:45.420Z",
        "lastUpdated": "2026-02-06T02:59:45.420Z",
        "gitCommitSha": "236752ad9ab36029b648bfd94707944760242768"
      }
    ]
  }
}
```

**Key observations:**
- Plugins are identified as `name@marketplace-name`
- Each entry tracks version, install path (under `~/.claude/plugins/cache/`), timestamp, and **git commit SHA**
- Scope: `user`, `project`, or `local`
- This is **generated by the CLI** — not meant to be hand-edited

### 1.2 Marketplace Registration

**File**: `~/.claude/plugins/known_marketplaces.json`

```json
{
  "claude-plugins-official": {
    "source": {
      "source": "github",
      "repo": "anthropics/claude-plugins-official"
    },
    "installLocation": "/home/wil/.claude/plugins/marketplaces/claude-plugins-official",
    "lastUpdated": "2026-08-07T03:52:06.423Z"
  },
  "wil-plugins": {
    "source": {
      "source": "git",
      "url": "https://github.com/wiltaylor/wil-plugins.git"
    },
    "installLocation": "/home/wil/.claude/plugins/marketplaces/wil-plugins",
    "lastUpdated": "2026-02-25T22:55:24.001Z"
  }
}
```

**Key observations:**
- Marketplaces store their **source URL/repo** and where they were cloned locally
- This is **generated by the CLI** — created via `claude plugin marketplace add`

### 1.3 Plugin Enable/Disable State (DECLARATIVE!)

**File**: `~/.claude/settings.json` → `enabledPlugins` section

```json
{
  "enabledPlugins": {
    "rust-analyzer-lsp@claude-plugins-official": true,
    "experts@wil-plugins": true,
    "playground@claude-plugins-official": true,
    "warp@claude-code-warp": true,
    "mattpocock-skills@claude-plugins-official": true
  }
}
```

**Key observations:**
- This **IS declarative** and can be hand-edited or managed by config tools
- Boolean value controls enable/disable state
- Changing this and restarting Claude Code will apply the state changes

### 1.4 Additional Marketplaces (DECLARATIVE!)

**File**: `~/.claude/settings.json` → `extraKnownMarketplaces` section

```json
{
  "extraKnownMarketplaces": {
    "claude-code-warp": {
      "source": {
        "source": "github",
        "repo": "warpdotdev/claude-code-warp"
      }
    }
  }
}
```

**Key observations:**
- This **IS declarative** — allows specifying additional marketplaces beyond the built-in defaults
- Can be hand-edited to add new marketplace sources
- Restarting Claude Code will recognize the new marketplaces

### 1.5 Plugin Blocklist

**File**: `~/.claude/plugins/blocklist.json`

```json
{
  "fetchedAt": "2026-04-14T23:59:44.394Z",
  "plugins": [
    {
      "plugin": "code-review@claude-plugins-official",
      "added_at": "2026-02-11T03:16:31.424Z",
      "reason": "just-a-test",
      "text": "This is a test #5"
    }
  ]
}
```

**Key observations:**
- Blocklist prevents specific plugins from being installed or used
- Can prevent enterprise users from installing problematic plugins
- Unclear if this is hand-editable or CLI-only — needs verification

### 1.6 Marketplace Index (Downloaded, Not Declarative)

**File**: `~/.claude/plugins/marketplaces/<name>/.claude-plugin/marketplace.json`

This is a **downloaded index** of all available plugins in a marketplace. It is NOT declarative:
- Contains 3,800+ lines of plugin definitions for the official marketplace alone
- Fetched from the marketplace source (e.g., GitHub repo)
- Contains plugin names, descriptions, sources, and download instructions
- **Plugin content itself** is stored in `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`

## 2. What the CLI Actually Does

### 2.1 Plugin Installation (`claude plugin install <name>`)

```bash
claude plugin install rust-analyzer-lsp@claude-plugins-official
```

**What happens:**
1. Looks up `rust-analyzer-lsp` in the marketplace `claude-plugins-official`
2. Reads the marketplace index to find the plugin's **source URL**
3. **Downloads/clones** the plugin from the source (GitHub, git URL, or local path)
4. Stores it in `~/.claude/plugins/cache/` under a versioned directory
5. Records the install in `installed_plugins.json` with timestamp and git commit SHA
6. **Non-interactive if run with `--config` flags** — doesn't prompt for user input

**Exit codes:** Scriptable (returns 0 on success, non-zero on failure)

### 2.2 Marketplace Registration (`claude plugin marketplace add <source>`)

```bash
claude plugin marketplace add https://github.com/wiltaylor/wil-plugins.git
```

**What happens:**
1. **Clones the marketplace repo** into `~/.claude/plugins/marketplaces/`
2. Reads the marketplace.json to validate it
3. Records the source in `known_marketplaces.json`
4. Updates `lastUpdated` timestamp

**Non-interactive:** Works without prompts

### 2.3 Plugin Enable/Disable (`claude plugin enable|disable`)

```bash
claude plugin disable warp@claude-code-warp
```

**What happens:**
1. Updates `enabledPlugins` in `settings.json`
2. Changes take effect after restart

**Note:** The settings.json can also be edited directly by hand or by a config management tool

### 2.4 CLI Output Formats

**Machine-readable JSON output available:**
```bash
claude plugin list --json
claude plugin marketplace list --json
```

**Example output:**
```json
[
  {
    "id": "rust-analyzer-lsp@claude-plugins-official",
    "version": "1.0.0",
    "scope": "user",
    "enabled": true,
    "installPath": "/home/wil/.claude/plugins/cache/...",
    "installedAt": "2026-02-06T02:59:45.420Z",
    "lastUpdated": "2026-02-06T02:59:45.420Z"
  }
]
```

**All commands return proper exit codes** (tested: `echo $?` shows 0 on success)

## 3. What Can Be Managed Declaratively

### Fully Declarative (Files-First):

1. **Plugin enable/disable state**
   - `settings.json` → `enabledPlugins`
   - Can write by hand or programmatically
   - Takes effect on restart

2. **Known marketplaces**
   - `settings.json` → `extraKnownMarketplaces`
   - Can declare additional marketplace sources
   - No network fetch needed once declared (though marketplace content requires an update)

3. **Plugin blocklist** (probably — implementation unclear)
   - `~/.claude/plugins/blocklist.json`
   - Can prevent enterprise users from using certain plugins

### Partially Declarative (Requires CLI Fetch):

1. **Plugin installation**
   - Can be declared as "plugin X@marketplace Y should exist at version Z"
   - But the **actual content must be fetched** via `claude plugin install`
   - Version detection works: `gitCommitSha` in `installed_plugins.json` allows convergence checks
   - Install is **non-interactive** when using `--config` flags — scriptable

2. **Marketplace registration**
   - Can declare a marketplace source in `extraKnownMarketplaces`
   - But the **index must be fetched** via `claude plugin marketplace add` or `claude plugin marketplace update`

## 4. Version Pinning & Convergence Detection

**Git commit SHA is tracked:**
```json
"gitCommitSha": "236752ad9ab36029b648bfd94707944760242768"
```

**How to detect installed version on disk:**
1. Read `~/.claude/plugins/installed_plugins.json`
2. Look up the plugin entry (e.g., `rust-analyzer-lsp@claude-plugins-official`)
3. Extract `version` and `gitCommitSha`
4. Compare with desired state

**Version constraints:** Not explicit in the installed metadata. Stored as simple semantic version (e.g., "1.0.0", "unknown" for dev versions).

✓ **Help system**: All commands have `--help` (e.g., `claude plugin install --help`)

## 7. Potential Issues for Declarative Management

1. **Plugin content is fetched, not declared**
   - The actual .js/.ts/.wasm files for a plugin come from a remote source
   - Declaring "plugin X should exist" requires an install operation
   - Unlike config files, you can't just write a plugin's code to disk

2. **Marketplace index is large**
   - Official marketplace.json is 3,800+ lines
   - This is downloaded and stored as-is
   - Not suitable for hand-editing or version control

3. **Auto-updates complicate state**
   - `autoUpdatesChannel: "latest"` in settings.json means plugins auto-update
   - A convergence check could report "installed version != declared version" if updates happen
   - Pinning requires either:
     - Disabling auto-updates globally
     - Storing exact git commit SHA and detecting on disk
     - Maintaining a lock file

4. **Installation timestamp vs. version**
   - `installed_plugins.json` tracks both version (semantic) and gitCommitSha
   - gitCommitSha allows precise version detection
   - But semantic versioning is ambiguous for "latest"

## 8. Proposed Declarative Resource Design

For a `claude_code` package managing plugins declaratively:

### Marketplace Resource
```wcl
resource "marketplace" "my_marketplace" {
  ensure      = :present
  name        = "wil-plugins"
  source_type = "github"
  repo        = "wiltaylor/wil-plugins"
}
```

**Implementation:** Write to `extraKnownMarketplaces` in settings.json; run `claude plugin marketplace add` (fetch) if not already present; verify presence in `known_marketplaces.json`.

### Plugin Resource
```wcl
resource "plugin" "rust_analyzer" {
  ensure          = :present
  name            = "rust-analyzer-lsp"
  marketplace     = "claude-plugins-official"
  version         = "1.0.0"  # or "latest"
  enabled         = true
  config          = { "some_key" = "value" }
}
```

**Implementation:**
- **Check phase**: Read `installed_plugins.json`, look for `rust-analyzer-lsp@claude-plugins-official`
  - Return installed version and git commit SHA
  - Return enabled state from `enabledPlugins` in settings.json
- **Apply phase**:
  - If not installed: run `claude plugin install rust-analyzer-lsp@claude-plugins-official --config ...`
  - Set enable/disable state in settings.json under `enabledPlugins`
  - Verify git commit SHA matches desired state (for version pinning)
- **Absence** (`ensure = :absent`): Remove from settings.json `enabledPlugins`, optionally run `claude plugin uninstall`

### Blocklist Resource
```wcl
resource "blocklist_entry" "code_review" {
  ensure = :present
  plugin = "code-review@claude-plugins-official"
  reason = "security"
}
```

**Implementation:** Write to `blocklist.json` (unclear if this can be hand-edited; needs verification).

## Answers to Research Questions

1. **What does `claude plugin install` and marketplace registration actually do?**
   - Install: Clones plugin source from remote, stores in cache, records in installed_plugins.json
   - Marketplace registration: Clones marketplace repo, records source in known_marketplaces.json

2. **Is marketplace registration reproducible by writing config alone, or does it require a fetch the CLI performs?**
   - Can declare in settings.json `extraKnownMarketplaces`, but **content fetch still required** (`claude plugin marketplace add`)
   - Once fetched, marketplace.json index is stored locally

3. **Can an installed plugin be declared by writing files, or must its content be fetched?**
   - Content **must be fetched** — plugins are binaries/code from remote sources
   - But the **declaration** (which plugin, what version) can be in config
   - Version is detectable via `gitCommitSha` in installed_plugins.json

4. **How is plugin version pinned, and how is an installed version detected on disk?**
   - Semantic version stored in installed_plugins.json
   - Git commit SHA also stored — allows precise version matching
   - Detect on disk: Parse installed_plugins.json, extract version + gitCommitSha

5. **Can enterprise settings mandate plugins or marketplaces?**
   - Partially: Blocklist mechanism could be pushed centrally
   - Marketplace sources can be declared in settings.json
   - No native "mandate plugins" feature observed

6. **Are CLI subcommands non-interactive and scriptable?**
   - Yes: `--json` output, proper exit codes, `--config` flag for non-interactive install
   - All commands have help (`--help`)

## Conclusion

**Plugins can use a mixed model for declarative management:**

| Aspect | Can Be Files-First? | Notes |
|--------|---------------------|-------|
| **Marketplace sources** | Yes, partially | Declare in settings.json; fetch via CLI |
| **Plugin enable/disable** | Yes | Direct settings.json editing |
| **Plugin installation** | No, CLI-dependent | Content must be fetched; declaration is possible |
| **Version detection** | Yes | gitCommitSha allows convergence check |
| **Plugin blocklist** | Unclear | blocklist.json structure known, editability unconfirmed |

**Recommendation for config-weave `claude_code` package:**
- **Plugin enable/disable**: Files-first via settings.json
- **Marketplace registration**: Declare in settings.json; shell out to `claude plugin marketplace` commands for initial fetch
- **Plugin installation**: Shell out to `claude plugin install`; use version/gitCommitSha for convergence checks
- **Posture**: Mostly files-first for config, CLI for fetch operations (justified by content fetching)
